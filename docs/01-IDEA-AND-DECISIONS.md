# DOOM on EVM — идея и история технических решений

> **Статус:** design baseline / передача в Codex · **Дата:** 2026-10-09 · **Проектное имя:** `doom-evm` (рабочее; `DOOM.sol` — допустимое название демо, **не** требование к одному файлу).
>
> **Прочитать вместе с:** [02 — техническая спецификация](02-TECHNICAL-SPECIFICATION.md), [03 — порядок работы и агенты](03-IMPLEMENTATION-PLAN.md).

## 1. Идея

Есть инженерный мем «*But can it run DOOM?*». Мы хотим сделать порт настоящего игрового движка DOOM на **Solidity (и при необходимости Yul)**, исполняемый **в Ethereum Virtual Machine**. В идеале в EVM происходят и игровой тик, и программный рендеринг каждого пикселя; браузер лишь посылает ввод и показывает готовый кадр.

Ценность двоякая:

1. **Демонстрация вычислительных возможностей EVM:** игра действительно работает в виртуальной машине, спроектированной для смарт-контрактов.
2. **Исследовательский, читаемый порт:** можно открыть `r_bsp.c` рядом с `r_bsp.sol`, сравнить функции и понять, как C-код 1990-х преобразуется в Solidity/Yul.

Это **не** продукт GameFi, не блокчейн-интеграция обычного WASM/JavaScript DOOM и не коммерчески целесообразная on-chain игра.

### Рабочая формулировка результата

> **DOOM runs inside the EVM. The DOOM engine is ported to Solidity/Yul.**

Не использовать абсолютные публичные утверждения «первый в мире», пока не проведён отдельный конкурентный аудит: отсутствие найденного порта **не доказывает** его несуществование.

## 2. Как мы пришли к архитектуре

### Решение 1. Порт движка, а не блокчейн-обвязка вокруг игры

**Рассматривали:**

- игровые правила в смарт-контракте, рендеринг в браузере;
- EVM-рендерер с упрощённой игровой моделью;
- порт оригинального DOOM на Solidity/Yul.

**Выбрали:** реальный DOOM как конечную цель. На ранних этапах допустима **частичная реализация оригинального движка** (сначала статичный кадр), но не отдельный raycasting-клон, выдаваемый за DOOM.

**Обоснование:** это и убедительнее для мема, и интереснее как сравнительный проект по исходникам.

### Решение 2. Не нужен Mainnet

Вначале обсуждали gas, code size, хранение ресурсов и стоимость кадров на Ethereum. Пользователь уточнил, что **даже локальный Anvil из Foundry с расслабленными ограничениями является успехом**.

**Выбрали:** Anvil и стандартная EVM-семантика. Можно ослабить ограничения размера контрактов, бюджета газа и памяти в рамках доступных параметров ноды. Не требуется оптимизация стоимости исполнения для Mainnet.

**Что не разрешаем:** специальный DOOM-precompile, нативный рендерер внутри форкнутой EVM, JavaScript-вычисление геометрии/света/видимости вместо контракта. Ослабление ресурсоёмких лимитов не должно подменять сам процесс исполнения.

**Нюанс:** `--disable-block-gas-limit` и большой `--gas-limit` не отменяют физическую память хоста, газ конкретного вызова и другие проверки; параметры и поведение проверяем экспериментально на закреплённой версии Foundry.

### Решение 3. Один `eth_sendTransaction` → один кадр через Event Log

Сравнивали три транспорта:

| Путь | Плюсы | Минусы | Статус |
|---|---|---|---|
| `tick(tx)` → `render(eth_call)` | Раздельные тик и рендер; нет истории кадров в логах | Два последовательных взаимодействия; состояние может измениться между ними | Запасной / отладочный |
| `tickAndRender(tx)` → `emit Frame(...)` → WS logs | Тик и кадр атомарны; один tx порождает один наблюдаемый результат; зрители могут подписаться | Доставка после майнинга; логи занимают место; транзакции последовательны | **Основной** |
| `step(state,input)` через один `eth_call` | Один round trip; без майнинга | Сложная сериализация полного состояния DOOM вне storage | Отложено |

**Выбрали:** контракт обновляет состояние, строит framebuffer, испускает событие с пикселями. Браузер подписывается на логи через WebSocket, а при пропуске сообщения может восстановить данные через receipt / `eth_getLogs`.

Ключевой принцип: **событие появляется после успешного исполнения транзакции и включения её в блок**, а не в момент инструкции `LOG` как потоковый вывод.

**Для рендер-демо до готовности игрового тика** допустима транзакция `renderFrame()` со статичной камерой; после внедрения симуляции целевой метод — `stepAndRender(input)`.

### Решение 4. 8-bit indexed framebuffer

У классического DOOM палитровое изображение. Начальный формат передачи: **по 1 байту на пиксель**, фиксированный порядок строк, `320 × 200` как цель, меньшие разрешения разрешены для экспериментов.

- `320 × 200 = 64 000 bytes` на кадр (без ABI-накладных расходов).
- Палитра предоставляется/загружается отдельно, с привязкой к версии ресурсов.
- В браузере допустимо декодировать индекс цвета в RGBA и вызывать `Canvas ImageData`: это **декодирование формата**, не перенос игрового рендерера в JS.

Сжатие/delta frames не нужны в MVP. История логов быстро растёт — принимаем это в локальной сессии.

### Решение 5. Сходство с оригинальным деревом исходников

Предложение положить всё в `DOOM.sol` отклонено. **Главная ценность** — исследователь видит путь каждой функции:

```text
original/linuxdoom-1.10/r_bsp.c  →  src/doom/r_bsp.sol
original/linuxdoom-1.10/r_segs.c →  src/doom/r_segs.sol
original/linuxdoom-1.10/m_fixed.c → src/doom/m_fixed.sol
```

**Выбрали:** один оригинальный `.c`-модуль, насколько возможно, соответствует одному `.sol`-модулю; прежние имена `R_`, `P_`, `G_`, `Fixed*` и приблизительный call graph сохраняются. Адаптации из-за EVM описываются рядом с кодом. `src/evm/Doom.sol` — только транспортный/интеграционный контракт, не склад всего движка.

В обычном случае используем Solidity `library` с `internal` функциями (компилятор объединяет их с потребителем). Но не требуем «один исполняемый контракт любой ценой», если размер/deployment окажутся препятствием: можно разнести исполняемый код по EVM-контрактам без смены исходной файловой карты.

### Решение 6. Состояние C и EVM

Глобальные переменные из оригинальных C-файлов логически группируются в **persistent game state (`storage`)** и **per-frame render state (`memory`)**. Указатели C заменяются ссылками через индексы/идентификаторы, сохраняя смысл и имена полей. Локальные переменные остаются локальными, если компилятор справляется.

**Почему:** storage переживает транзакции; memory подходит для промежуточных массивов (clipping, drawsegs, visplanes, framebuffer). Это ограниченное, документируемое отклонение от C, не переизобретение игрового движка.

### Решение 7. Stack too deep: учитывать заранее, рефакторить по факту

Пользователь указал на свой опыт со `Stack too deep` в Solidity. **Риск существенен** для крупных функций вроде `R_StoreWallRange()`.

**Выбрали стратегию:**

1. С самого начала включить `via_ir = true`, optimizer.
2. Сразу определить понятные `storage`/`memory` контексты; не раздувать сигнатуры.
3. Не переносить все локальные переменные в структуры заранее — это ухудшит соответствие исходнику.
4. При ошибке сначала разобраться с областями жизни переменных/временным `memory`-контекстом, только затем делить оригинальную функцию на маленькие helper-функции **в том же файле**.
5. Yul применять локально, где требуется; `assembly ("memory-safe")` — **только если это действительно доказано**.
6. Лимит физического стека EVM (1024 слова) остаётся; рекурсивный BSP-обход тестируем на реальных картах, при необходимости переписываем на явный стек в `memory` с документированным отклонением.

### Решение 8. Портировать от настоящих исходников, проверять поведением

**Выбрали:** за основу конкретный зафиксированный commit [id-Software/DOOM / `linuxdoom-1.10`](https://github.com/id-Software/DOOM/tree/master/linuxdoom-1.10). Chocolate Doom — **дополнительный** эталон/инструмент для воспроизведения, но его код нельзя незаметно объявить «оригиналом».

Проверки: C-vs-Solidity unit vectors → совпадение промежуточных результатов рендеринга → сравнение пикселей при том же WAD/камера/настройках. Любое намеренное несовпадение объясняется.

### Решение 9. Сначала настоящий статичный кадр, затем игра

**Первый важный результат:** статичный кадр настоящего Doom-совместимого уровня, пройденный через BSP и отрендеренный Solidity/Yul внутри Anvil, опубликованный в Event Log. Дальше камера, физика, тик, монстры и оружие.

Сразу разворачивать полный оригинальный игровой цикл необязательно. Однако математические и рендеринговые функции должны вести к порту настоящего DOOM, а не одноразовой демонстрации.

## 3. Что считаем успешным

| Этап | Проверяемый результат |
|---|---|
| M1 — DOOM rendered by EVM | Реальная геометрия/текстуры карты из WAD, реальный программный рендерер в Solidity/Yul, EVM отдаёт изображение через Frame event; браузер не считает игровой кадр |
| M2 — DOOM playable on EVM | Повороты и движение по карте, столкновения, корректный игровой мир; ввод → EVM → framebuffer |
| M3 — DOOM running on EVM | Существенные базовые игровые механики DOOM: враги, оружие, двери, игровые тики, повреждения и взаимодействие |

**Нет** порога FPS, бюджета gas или требования Mainnet. Метрики всё равно собираем для честного отчёта.

## 4. Сознательно отложено / открытые вопросы

| Вопрос | Текущая позиция |
|---|---|
| Какую версию solc и Foundry закрепить? | Выбрать и зафиксировать в bootstrap после проверки `anvil --help`, `forge --version`, `solc --version`; пример конфигурации во 2-м документе — не протокол испытаний |
| Как хранить WAD-данные? | TypeScript build-time preprocessing допустим; формат контрактных данных после измерения загрузки/чтения; алгоритмические расчёты кадра строго EVM |
| Сколько storage нужно для уровня? | Оценить на реальном WAD, разделять immutables и изменяемое состояние |
| Будет ли единственный контракт? | Не требование. Source fidelity важнее единого runtime bytecode |
| Первый ресурсный пакет? | Для публично воспроизводимого демо — **Freedoom: Phase 1**; его E1M1 **не является** оригинальным коммерческим E1M1. Для приватного сравнения разрешён пользовательский законно полученный оригинальный WAD |
| Изображение без HUD / статус-бара? | Сначала world view, потом полный 320×200 кадр, HUD и weapon sprites; чётко маркировать частичный рендер |
| Звук, сеть, сохранения, multiplayer? | Не входят в первый цикл |
| «Первый DOOM на EVM»? | Гипотеза, не подтверждённое первенство |

## 5. Инварианты, которые Codex не должен менять без обсуждения

1. Игра и рендеринг выполняются **в обычных EVM opcode**, сгенерированных из Solidity/Yul.
2. Не подменять движок JavaScript, WebAssembly, Rust, специальными precompiles.
3. По возможности **параллельное соответствие C ↔ Solidity**: названия модулей/функций и последовательность алгоритмов.
4. Не отказываться от original BSP renderer ради простого raycaster как итоговой реализации.
5. Основной транспорт: **одна транзакция** генерирует **один кадр в логе**; `eth_call` остаётся допустимым диагностическим транспортом.
6. Каждое существенное расхождение с C документировать и проверять тестами.
7. Никаких заявлений о скорости, пиксельной точности или оригинальности без измерений/сравнений.
